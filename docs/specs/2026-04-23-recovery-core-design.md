# Recovery Core Design

## Контекст

Текущий MVP уже умеет:
- хранить привычки локально;
- работать по недельному расписанию;
- отмечать выполнения;
- считать `XP`, уровень, streak и достижения;
- показывать базовую статистику;
- использовать локальные уведомления.

Следующий шаг развития продукта: превратить приложение из обычного трекера привычек в систему поддержки ритма. Главная ценность нового модуля не в том, чтобы сильнее давить на пользователя за пропуски, а в том, чтобы помочь не выпадать из процесса в периоды спада.

## Цель модуля

`Recovery Core` добавляет в приложение адаптивную механику мягкой поддержки. Система должна:
- замечать признаки повышенного риска срыва;
- объяснять решение коротко и понятно;
- предлагать пользователю облегченный день вместо полного выпадения из плана;
- сохранять ощущение контроля у пользователя;
- давать предметный задел под будущую магистерскую работу.

## Продуктовая идея

Приложение должно поддерживать не только "идеальные" дни, но и плохие дни. Вместо бинарной модели "выполнил все / сорвался" появляется промежуточный режим: пользователь может временно снизить нагрузку и удержать базовый ритм.

Это делает продукт:
- полезнее в реальном повседневном использовании;
- сильнее как курсовую работу, потому что в системе появляется адаптивная логика;
- перспективным как research foundation для последующей персонализации.

## Основной сценарий дня

Утром, при первом открытии приложения, пользователь проходит короткий `daily check-in`.

Check-in должен занимать 10-20 секунд и содержать 3 сигнала:
- `энергия`;
- `нагрузка`;
- `настроение`.

После check-in система использует:
- ответы пользователя;
- текущий `streak`;
- недавние пропуски;
- объем плана на сегодня;
- приоритеты привычек.

На основании этих данных приложение определяет статус дня и, при необходимости, предлагает облегченный режим.

## Статусы дня

Для `v1` вводятся три статуса:
- `Нормальный день`
- `Напряженный день`
- `День восстановления`

Смысл статусов:
- `Нормальный день`: пользователь в рабочем состоянии, стандартный план сохраняется без изменений;
- `Напряженный день`: заметен риск перегруза, но система пока не считает ситуацию критичной;
- `День восстановления`: риск срыва высокий, и пользователю нужно предложить заметное снижение нагрузки на текущий день.

## Подход к оценке состояния

Логика для `v1` должна быть средней сложности:
- не слишком примитивной;
- без ML;
- без переусложненной математики;
- объяснимой на защите.

Подход: `rule-based scoring`.

Идея:
- каждому сигналу назначается вес;
- факторы текущего состояния и недавнего поведения суммируются;
- итоговая оценка переводится в один из 3 статусов дня.

Это решение выбрано потому что:
- его легко реализовать поверх текущего оффлайн-MVP;
- оно выглядит достаточно содержательно для курсовой;
- позже его можно заменить или расширить более интеллектуальной моделью.

## Объяснимость решения

Система должна объяснять решение кратко.

Формат объяснения:
- 1-2 короткие причины;
- без показа "сырой" формулы;
- без ощущения черного ящика.

Примеры объяснения:
- "Сегодня высокая нагрузка и низкая энергия."
- "Есть недавние пропуски, поэтому лучше снизить план."
- "Настроение стабильное, поэтому можно оставить обычный ритм."

Это обеспечивает баланс:
- UX остается простым;
- логика решения видна пользователю и преподавателю;
- система не выглядит магической.

## Облегченный день

Если система определяет повышенный риск срыва, она не должна автоматически менять все привычки без согласия пользователя. Вместо этого приложение предлагает `облегченный день`.

Принципы облегченного дня:
- решение предлагается, а не навязывается;
- полный список привычек не удаляется;
- приложение лишь сокращает дневной фокус;
- пользователь понимает, что происходит и почему.

## Ограничение нагрузки

В `облегченном дне` по умолчанию остаются `до 3 привычек`.

Почему выбрано именно `3`:
- `1` слишком жестко и превращает день в формальность;
- `2` уже рабочий вариант, но может быть слишком мало;
- `3` все еще заметно снижает нагрузку, но оставляет ощущение продуктивного дня.

Правило для `v1`:
- система предлагает оставить до 3 самых важных привычек;
- если приоритетных привычек меньше, остаются только они;
- остальные привычки не удаляются, а уходят из фокуса на текущий день.

## Приоритет привычек

Для отбора привычек в облегченный день используется `ручной приоритет`.

Причины выбора:
- логика прозрачна;
- пользователь сохраняет контроль;
- поведение системы легко объяснить;
- rule-based механизм не превращается в неочевидную "магию".

Практический смысл:
- у привычки появляется уровень важности;
- recovery-система использует его при сокращении дневного плана;
- пользователь заранее определяет, что для него критично даже в тяжелые дни.

## Что должно измениться в продукте

После внедрения `Recovery Core` приложение должно уметь:
- запрашивать утренний `daily check-in`;
- вычислять статус дня;
- кратко объяснять причину статуса;
- предлагать облегченный день;
- показывать сокращенный дневной фокус;
- использовать ручной приоритет привычек для выбора основных задач дня;
- хранить историю recovery-решений.

## Польза для курсовой

`Recovery Core` усиливает проект сразу по нескольким направлениям:
- добавляет адаптивное поведение поверх существующего CRUD/MVP;
- показывает работу не только с данными, но и с прикладной логикой принятия решений;
- демонстрирует осмысленный UX-сценарий поддержки пользователя;
- дает более содержательное обоснование архитектурных решений.

На защите это можно подавать как:
- модуль поддержки устойчивости поведения;
- механизм профилактики срыва;
- пример explainable rule-based адаптации плана дня.

## Задел под магистерскую

`Recovery Core` специально проектируется как переходный слой между простым MVP и будущей исследовательской системой.

Дальнейшее развитие может включать:
- персонализированную модель риска срыва;
- адаптивный лимит привычек вместо фиксированного значения `3`;
- более сложный расчет факторов состояния;
- аналитику влияния recovery-дней на удержание привычек;
- персональные рекомендации на основе накопленного поведения.

Таким образом, текущая версия остается понятной и реализуемой, а архитектурно открывает путь к магистерской диссертации.

## Границы `v1`

Что входит в `v1`:
- короткий утренний check-in;
- rule-based оценка состояния;
- 3 статуса дня;
- короткое объяснение решения;
- предложение облегченного дня;
- ограничение до 3 привычек;
- ручной приоритет привычек.

Что не входит в `v1`:
- machine learning;
- скрытая автоматическая перестройка системы без участия пользователя;
- сложные психологические профили;
- богатый дневник самонаблюдения;
- слишком тяжелая аналитика.

## Итог

`Recovery Core` — это следующая сильная фича для проекта, потому что она:
- реально полезна в жизни;
- убедительно выглядит для курсовой;
- не ломает текущий MVP;
- открывает прямой путь к более серьезному исследовательскому развитию.

## Implemented v1 completion scope

Фактически реализованный `v1` завершает `Recovery Core` без новой вкладки и разводит сценарии по уже существующим экранам:
- `Сегодня` отвечает за `daily check-in`, показ статуса дня, объяснение причин и явное действие `Принять облегченный день`;
- после принятия облегченного дня блок `Сегодняшний фокус` фильтруется до `suggestedHabitIds`, а остальные привычки остаются доступны на экране `Мои привычки`;
- `Статистика` показывает `Recovery review за неделю`, completion rate для recovery и обычных дней, историю последних recovery-дней и блок `Почему был сложный период`;
- данные сохраняются локально в SQLite через `daily_check_ins` и `recovery_day_entries`, где дополнительно хранятся `lightPlanAccepted` и `lightPlanAcceptedAt`;
- weekly review считается по последним 7 календарным дням, difficult period insight — по последним 14 дням;
- решение о переходе в облегченный день остается за пользователем, XP и completion-логика не меняются.
